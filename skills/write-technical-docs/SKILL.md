# Write technical docs

Identify the reader's job: learning with a working example, completing a task, looking up facts, or understanding a design. Keep the document centered on that job. Put prerequisites before the first dependent step, show exact commands and expected outcomes, and distinguish examples from requirements.

Lead with the action or answer. Prefer concrete verbs, the project's terminology, and short paragraphs with the condition before the instruction it qualifies. Remove generic praise, vague claims, repeated summaries and overly compressed jargon. Match the user's tone and preserve meaning, examples, warnings and source links that carry information.

When editing a guide, confirm paths, flags, expected output and version-sensitive facts against code or primary documentation. Avoid promising behavior you did not verify. For a plain-language restatement, preserve decisions and uncertainty without adding new advice.
