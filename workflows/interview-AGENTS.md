# Interview Coding Defaults

- For code generation, apply `$ponytail`: use standard library tools, keep existing signatures, and make the smallest correct change.
- For a new interview problem or ambiguous feature request, apply `$interview-copilot` and `$interrogate`: give the three-bullet plan and 3–5 relevant edge cases before implementation. Provide full code when requested.
- When asked to create, refine, or stress-test project vision or contribution criteria, use `$vision`. Ground it in real repository history and obtain the author's approval before writing the vision. Existing approved vision guides later design choices; ordinary coding tasks do not start the interactive vision process.
- In an unfamiliar multi-file repo, use `$how` to trace the relevant flow and `$blast-radius` before structural edits.
- For a wrong answer, failing test, or timeout, use `$systematic-debugging` to reproduce and identify the false assumption before patching.
- Before declaring an implementation complete, use `$unslop` for a brief code polish and `$verification-before-completion` for relevant local checks.

Follow the target repository's language, tests, and task-specific instructions. Keep interview responses concise unless more detail is requested.
